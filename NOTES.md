# Заметки о реализации MVP

Документ фиксирует толкования `Архитектура.md` там, где он неоднозначен, умалчивает или
противоречив, а также осознанные отступления и найденные проблемы спецификации.
Сам `Архитектура.md` не изменялся. При выборе толкования приоритет у принципа
безопасного отказа (1.1.3), изоляции данных и машины состояний (2.3.4).

## 1. Толкования

### Инфраструктура и структура проекта

- **Размещение кода без отдельных модулей (3.4.2).** Структура проекта не предусматривает
  модулей для логирования и общих веб-помощников, а лишних файлов добавлять нельзя.
  Поэтому настройка логирования и фильтр маскирования access-лога находятся в
  `app/config.py` (стартовая конфигурация процесса, используется и web, и worker), а общие
  элементы веб-слоя (шаблоны, коды ошибок 3.1.3, обработчики ошибок, зависимости
  аутентификации, форматирование) — в `app/routes/__init__.py`.
- **Миграции.** Эталонная схема 2.3.1 создаётся цепочкой Alembic-ревизий: `0001` —
  `system_state` (нужна на этапе 1 для heartbeat и `/healthz`), `0002` — остальные таблицы.
  DDL в миграциях повторяет эталонный SQL дословно.
- **Сборка образа (3.4.3).** Индекс PyTorch задан аргументом сборки `TORCH_INDEX_URL` со
  значением по умолчанию из спецификации (`https://download.pytorch.org/whl/cpu`), языки
  весов EasyOCR — аргументом `OCR_LANGS=ru,en` (веса скачиваются «для `OCR_LANGS`»).
  Порядок слоёв: шрифт → PyTorch → стек OCR и веса → зависимости приложения → код;
  списки зависимостей извлекаются из `pyproject.toml` в отдельной стадии сборки, поэтому
  изменение кода (и даже зависимостей приложения) не пересобирает тяжёлые слои.
  `.dockerignore` не предусмотрен структурой, поэтому `COPY` перечисляет только нужные
  каталоги — `.env` и `.git` в образ не попадают. Процессы работают от непривилегированного
  пользователя `app`.
- **Версии зависимостей.** Все прямые зависимости закреплены точными версиями в
  `pyproject.toml`; `torch==2.14.0` и `torchvision==0.29.0` закреплены в `Dockerfile`
  (ставятся из CPU-индекса). Дополнительно закреплены значимые транзитивные зависимости:
  `starlette`, `limits`, `numpy`, `opencv-python-headless`. Для OpenCV выбрана ветка 4.x
  (4.14.0.94), а не вышедшая 5.0: EasyOCR 1.7.2 разрабатывался под 4.x. Образы также
  закреплены: `python:3.12.14-slim`, `postgres:16.15`, `axllent/mailpit:v1.31.2`,
  `caddy:2.11.4`.
- **Пароль PostgreSQL.** В 3.4.1 нет переменной для пароля контейнера `db`, а в
  эксплуатации пароль должен быть стойким. Добавлена переменная `POSTGRES_PASSWORD`
  (в `.env.example` с пояснением); она должна совпадать с паролем в `DATABASE_URL` и
  `TEST_DATABASE_URL`.
- **Порты в разработке** (`8000`, `8025`, `1025`) публикуются только на `127.0.0.1`.
- **Служебные страницы FastAPI** (`/docs`, `/redoc`, `/openapi.json`) отключены: это были бы
  эндпоинты сверх перечня 3.1.2.

### Конфигурация и логирование

- **Проверки при старте (3.4.1)** реализованы валидаторами `Settings`; при ошибке web
  (импорт `app.main`) и worker (`python -m app.worker`) печатают «Ошибка конфигурации» с
  перечнем причин без значений переменных и завершаются с кодом 1. Дополнительно
  отклоняются заведомо бессмысленные значения (неположительные лимиты и сроки, порог
  вне 0–100, неизвестный `DISPLAY_TZ`).
- **Логи (3.2.10).** Формат: время, уровень, имя логгера, `request_id` (если известен),
  сообщение. Логгеры uvicorn направлены в общий обработчик stdout; фильтр маскирования
  токенов стоит и на логгере `uvicorn.access` (изменяет запись до любых обработчиков), и на
  обработчике stdout. Логгеры `sqlalchemy`, `PIL`, `multipart` и др. понижены до WARNING:
  иначе при уровне DEBUG SQLAlchemy выводит строки результатов, где есть ФИО и email.
  Движок БД создаётся с `hide_parameters=True`, чтобы значения параметров не попадали в
  тексты исключений.

### Порядок этапов

- **Критерии этапа 3 опираются на маршруты последующих этапов (4.3).** AT-01 проверяет
  `POST /heirs` до подтверждения email, AT-03 — CSRF на `/heirs`, `/heir/login` и
  `/cancel/{token}`, AT-06 — лимит наследников, AT-07 — изоляцию наследников и отмену
  запросов. Чтобы критерий этапа 3 выполнялся буквально, на этапе 3 полностью реализованы
  маршруты наследников (этап 4), вход и выход наследника (этап 5), список запросов, отмена
  из кабинета и по ссылке (этап 7). Порядок этапов сохранён: последующие этапы добавляют
  свои приёмочные тесты и остальную функциональность.

### Владелец и записи

- **Параметр `next` (3.1.1)** дополнительно отклоняется, если содержит обратную косую черту
  или управляющие символы: браузеры трактуют `/\evil.com` как `//evil.com` (открытое
  перенаправление). `next` добавляется только при перенаправлении GET-запроса: после входа
  повторить POST невозможно.
- **«Сессия истекла, войдите снова» (3.3.5)** показывается при любом перенаправлении с
  маршрута Владельца на `/login`: истёкшую подписанную cookie браузер не присылает, и
  отличить истёкшую сессию от отсутствующей нельзя.
- **Регистрация** выполняет вход (3.1.2), поэтому устанавливает `last_login_at`; событие
  `LOGIN_SUCCEEDED` при этом не пишется (есть `USER_REGISTERED`). При успешной отправке E1
  показывается flash «Письмо отправлено», при неудаче — `EMAIL_SEND_FAILED`.
- **Подтверждение email** идемпотентно: повторный переход по действующей ссылке не пишет
  второе событие `EMAIL_VERIFIED`. Повторная отправка при уже подтверждённом email письмо не
  отправляет. Перенаправление «назад» после `POST /verify-email/resend` выполняется по
  скрытому полю `next` (заголовок Referer не отправляется из-за `Referrer-Policy: no-referrer`).
- **Вход по несуществующему email** проверяет пароль против фиктивного argon2-хеша, чтобы
  время ответа не раскрывало наличие аккаунта; событие `LOGIN_FAILED` пишется только для
  существующего email (у события обязателен `user_id`).
- **ФИО:** пробельные последовательности схлопываются в один пробел, «буквы» — любые буквы
  Unicode (`str.isalpha`), обязательна хотя бы одна буква.
- **Длина текста записи** считается в символах Unicode после замены `CRLF` на `LF` (браузер
  отправляет переводы строк как `CRLF`, а счётчик на странице считает их одним символом).
  Пустой текст допустим: спецификация задаёт только верхнюю границу.
- **Мегабайт** в лимитах и сообщениях — 1 МиБ (1 048 576 байт).
- **Потоковое чтение загрузки (2.2.2).** Тело формы с файлом читается с ограничением
  `MAX_FILE_MB` (`MAX_DOC_MB` для документа) + 64 КиБ на служебные поля; при превышении
  чтение прерывается и возвращается `413 FILE_TOO_LARGE`. CSRF-токен находится в теле формы,
  поэтому для слишком большого тела `413` возникает раньше проверки CSRF. Точный размер файла
  проверяется после разбора формы.
- **Порядок проверок при создании записи:** сессия → CSRF → поля (400) → формат (415) →
  размер (413) → лимиты (409). Проверка лимитов выполняется под блокировкой строки Владельца,
  чтобы параллельные запросы не превысили лимит.
- **Имя файла** сохраняется без компонентов пути и непечатаемых символов; в
  `Content-Disposition` передаётся через `filename*=UTF-8''…` с ASCII-заменой в `filename`.
- **TXT** проверяется декодированием всего файла как UTF-8; файл без расширения отклоняется.
- **Отсутствующий файл записи** при скачивании Владельцем — внутренняя ошибка (500, лог ERROR).
- **Сообщение `LIMIT_EXCEEDED`**: «Достигнут лимит: записи (2 из 2)», «… наследники (1 из 1)»,
  «… объём файлов (0,6 из 1 МБ)».

### Наследники и отмена

- **`GET /heirs/new` без подтверждённого email** возвращает ту же страницу ошибки
  `403 EMAIL_NOT_VERIFIED`, что и `POST /heirs`.
- **Гонки с подачей запроса.** Перевыпуск ключа и удаление наследника блокируют строку
  наследника (`SELECT … FOR UPDATE`); подача запроса (этап 5) блокирует ту же строку, поэтому
  проверка «нет активного запроса» не может устареть.
- **Удаление наследника (2.3.3)** считает, что документов у завершённых запросов нет, но шаг E
  Worker может ещё не успеть их удалить. Поэтому после фиксации транзакции Web удаляет
  оставшиеся файлы документов этого наследника — иначе строки запросов исчезнут каскадом, а
  файлы останутся навсегда.
- **Вход наследника** очищает сессию целиком и выдаёт новый CSRF-токен (как вход Владельца):
  защита от фиксации сессии и от смешения ролей в одном браузере.
- **`/cancel/{token}`:** неверная подпись → `400 INVALID_TOKEN`; подпись верна, но запроса
  нет (удалён вместе с наследником или аккаунтом) → `404 NOT_FOUND`. Страница отдаётся с
  `Cache-Control: no-store`: её адрес содержит секретный токен. После отмены сообщение
  «Запрос отменён. Ключ наследника отозван…» передаётся flash-сообщением.

### Портал наследника

- **Состояние «Есть запрос `RELEASED`» и скачивание `/heir/files/{record_id}`** реализованы на
  этапе 5 вместе с остальными состояниями портала (3.3.3): иначе кнопки «Скачать» вели бы на
  несуществующий маршрут. Приёмочные тесты выдачи (AT-13, AT-14) — на этапе 7.
- **Проверки при подаче (2.2.4):** активный запрос ищется по наследнику (по любому его
  ключу), выданный — по текущему ключу. Подача блокирует строку наследника и после блокировки
  повторно проверяет, что ключ не отозван; уникальный частичный индекс дополнительно защищает
  от двойной подачи.
- **Суточный лимит** учитывает запросы по ключу с `created_at > now − 24 ч` (граница строгая:
  ровно через 24 часа подача снова возможна), кроме отклонённых с `OCR_UNAVAILABLE`.
- **Неверный контактный email** — `400 VALIDATION_ERROR` с повторным показом портала и
  введённым значением.
- **Причины отказа** в портале выводятся элементами с `data-error-code="<код причины>"`
  (3.1.1: у каждого сообщения об ошибке есть этот атрибут), совет по съёмке — под списком.
- Если после выдачи Наследнику не назначено ни одной записи, портал сообщает об этом
  («Владелец не назначил вам ни одной записи»): спецификация этот случай не описывает.
- События `HEIR_DATA_VIEWED` и `HEIR_FILE_DOWNLOADED` привязаны к выданному запросу
  (`request_id`).

### Проверка документа

- **Нормализация (3.2.8).** «Кириллические буквы» — прописные `А–Я` (Ё к этому моменту заменена
  на Е), «цифры» — `0–9`. Части ФИО нормализуются той же функцией, поэтому ФИО, записанное
  латиницей, по построению правил не может совпасть (сверка рассчитана на паспортное ФИО
  кириллицей, 1.1.1).
- **R3** ищет и перекрывающиеся совпадения шаблона даты (обёртка `(?=(…))`), чтобы соседние
  даты не «съедали» друг друга.
- **Порог `T`** берётся из `RULE_FUZZY_THRESHOLD`; у `check()` есть необязательный параметр
  `threshold` для явной передачи порога, сигнатура из 3.2.8 сохранена.
- **Защита от «бомб» в PDF.** Pillow ограничивает размер изображения (`MAX_IMAGE_PIXELS`), но
  PDF рендерится PyMuPDF до Pillow. Поэтому первая страница, которая при `PDF_RENDER_DPI` дала
  бы больше 50 млн пикселей, считается нечитаемой, не рендерясь (5.2.3: «Декомпрессионные
  бомбы»). Для JPG/PNG действует штатное поведение Pillow: предупреждение выше 50 млн
  пикселей и `DecompressionBombError` выше 100 млн.
- **Зашифрованный PDF** (`is_encrypted` или `needs_pass`) нечитаем, даже если открывается без
  пароля, — дословно по 3.2.7.
- **PyMuPDF** импортируется как `pymupdf` (под псевдонимом `fitz`): в версии 1.28 импорт `fitz`
  выдаёт предупреждение об устаревании, API тот же.
- **Наблюдение для калибровки (4.5).** На синтетических свидетельствах EasyOCR распознаёт знак
  `№` как `Ng`, из-за чего R4 не срабатывает и решение держится на R5 («ЗАГС»). Регулярное
  выражение R4 не менялось: оно задано спецификацией и подлежит калибровке на реальных
  образцах.

### Worker

- **Дата окончания ожидания в E2** вычисляется непосредственно перед отправкой, а
  `waiting_until` в БД — от момента приёма письма SMTP-сервером (2.2.6 п. 2). Поэтому
  фактический срок никогда не раньше указанного в письме (на время SMTP-сессии позже).
  Аналогично E3 содержит `max(waiting_until, now + REMINDER_BEFORE_SECONDS)`, вычисленное до
  отправки.
- **Шаг D** перед `transition()` перепроверяет условия выдачи (`waiting_until ≤ now`,
  напоминание отправлено) под блокировкой строки `FOR UPDATE`. Спецификация предполагает один
  экземпляр Worker; перепроверка гарантирует, что и при ошибочно запущенном втором экземпляре
  продление срока шагом C не будет обойдено (принцип безопасного отказа).
- **Шаг A:** увеличение `ocr_attempts` и переход в `REJECTED` с `OCR_UNAVAILABLE` выполняются в
  одной транзакции; увеличение условно (`status = 'PENDING_REVIEW'`), поэтому отменённый во
  время OCR запрос не изменяется. Расшифрованный документ и распознанный текст освобождаются
  сразу после использования.
- **Ошибка инициализации OCR при старте Worker** завершает процесс с кодом 1: heartbeat
  прекращается, `/healthz` сообщает `degraded`, выдача и уведомления только задерживаются.
- Служебные обновления (`ocr_attempts`, напоминание, `doc_stored`) также обновляют `updated_at`.

### P1: письма E4–E9, изменение ФИО, резервное копирование

- **Письма P1** отправляются одной попыткой **после** фиксации перехода: E4 и E6 — после
  отклонения (в том числе с `OCR_UNAVAILABLE`), E7 — после начала ожидания, E5 и E8 — после
  выдачи, E9 — после отмены из кабинета или по ссылке. Ошибка отправки только пишется в лог и
  не влияет на статус; повторной отправки нет («без повторов», 3.2.6).
- **Содержимое E4** («имя наследника, дата»): указаны дата подачи и дата отклонения, ссылка на
  список наследников для перевыпуска ключа. E5 дополнительно напоминает, что закрыть доступ
  можно перевыпуском ключа (3.2.2 п. 7).
- **Изменение ФИО (FR-19):** проверка «нет активных запросов» выполняется под блокировкой строк
  наследников Владельца — тех же строк, что блокирует подача запроса, — поэтому активный запрос
  не может появиться между проверкой и изменением. Порядок проверок: CSRF → `409 PROFILE_LOCKED`
  → поля (400). Правила полей те же, что при регистрации.
- **`scripts/backup.sh`** (4.5 п. 6): `pg_dump -Fc` и `tar` тома `files` через контейнер worker,
  файлы создаются с правами `600` через временное имя, хранение `BACKUP_KEEP_DAYS` (14) дней,
  копирование во внешнее хранилище — `rsync --delete` в `BACKUP_REMOTE`, если он задан
  (конкретное хранилище спецификацией не определено). Каталог `backups/` исключён из Git.
  Переменные скрипта (`BACKUP_DIR`, `BACKUP_KEEP_DAYS`, `BACKUP_REMOTE`) относятся к скрипту,
  а не к приложению, поэтому описаны в README, а не в `.env.example`.

### Удаление аккаунта

- После фиксации транзакции удаляются файлы всех файловых записей и документы **всех**
  запросов Владельца (а не только с `doc_stored = true`): отсутствие файла ошибкой не
  считается, а лишний файл документа не должен пережить аккаунт. Событие аудита не пишется:
  журнал удаляется вместе с аккаунтом (1.2.5).

### Интерфейс

- **Страницы ошибок** содержат кнопку «На главную» (`/vault`, `/heir/portal` или `/`).
  Кнопка «Назад» потребовала бы JavaScript `history.back()` или заголовок Referer, который не
  отправляется; спецификация допускает любую из двух кнопок.
- Ошибки HTTP вне списка 3.3.4 (например, `405 Method Not Allowed`) отдаются стандартным
  ответом FastAPI.
- **Pico.css и CSP.** Встроенные `data:`-иконки Pico (галочка чекбокса, спиннер `aria-busy`,
  значок `aria-invalid`) блокируются политикой `default-src 'self'`. Их CSS-переменные
  переопределены в `app.css` значением `none`, чекбоксы и списки используют нативный вид —
  в консоли браузера нет нарушений CSP (проверено в Chromium).
- **Таблица запросов на экранах до 576 px** показывается карточками с подписями полей
  (CSS `attr(data-label)`): при ширине 360 px кнопка «Отменить» иначе оказывалась за
  пределами экрана. Разметка остаётся таблицей, как в 3.3.2.
- **Счётчик символов «N / 10 000»** обновляется скриптом `app.js`. В 2.1.1 перечень задач
  JavaScript закрыт, но 3.3.2 требует счётчик, а 3.3 — `confirm()` из `app.js`; без скрипта
  счётчик показывает значение на момент открытия формы.

### Тесты

- **Детерминированный профиль test.** `tests/conftest.py` удаляет из окружения все
  переменные приложения и задаёт профиль test (3.4.1): база `app_test`, `memory`, `fake`,
  тестовые `SECRET_KEY`/`MASTER_KEY`. Остальные параметры берут значения по умолчанию из
  3.4.1, поэтому настройки `.env` (например, укороченный период ожидания для ручной
  проверки 4.6) не влияют на тесты.
- **Часы в тестах** замораживаются в начале каждого теста на текущем времени.
- **AT-27** выполняет сценарий AT-13 через настоящий сервер uvicorn в отдельном потоке, чтобы
  перехватить реальный access-лог. Из перехвата исключены только логгеры HTTP-клиента самого
  теста (`httpx`, `httpcore`): это не логи приложения, и они по определению содержат URL
  запросов клиента.
